# SVNC 接入协议规范

状态：项目标准草案 v0.1
日期：2026-11-24
范围：记录当前工作区已经实现的接入约定，作为后续互通与兼容性维护的依据。

本文尚未冻结为 v1.0，也不表示已经成为行业标准或完成 IANA 注册。第 1–9 节定义草案基线，第 10 节列出正式发布前的工作；其中的提案不能被客户端视为服务端已实现的能力。

## 1. 定位与边界

### 1.1 协议与产品命名

**SVNC 是协议名，JumpVNC 是产品名。** JumpVNC 是由 JumpServer 团队开发的远程桌面产品，客户端与服务端分别称为 JumpVNC Viewer 和 JumpVNC Server；本仓库中的实现作为 SVNC 的参考实现维护。

| 名称或标识 | 含义 |
| --- | --- |
| SVNC / `svnc` | 协议名称 / 供资产与连接系统区分接入方式的类型标识 |
| JumpVNC | 实现 SVNC 的产品，不作为线上握手字段 |
| VNC / `vnc` | 普通 VNC 接入类型；桌面使用 RFB，不能直接连接 SVNC 的 SSH 入口 |
| SSH 子系统名 `vnc` | SSH 认证后的桌面服务选择，与资产类型 `vnc` 属于不同命名空间 |

第三方可以独立实现 SVNC 客户端、服务端或网关，不要求使用 JumpVNC 品牌，也不要求部署 JumpServer。互通以公开规范和已声明能力为依据，不依赖某个产品版本、私有配置格式或特定桌面后端。当前规范仍是 v0.1 草案，后续标准化工作见第 10 节。

现有二进制名 `jumpvnc` / `svnc-desktop`、应用包名 `JumpVNC.app` 和仓库目录名属于实现命名。`.svnc` 是当前客户端的连接文件格式，可记录多种连接方式；其文件版本也不是线上协议版本，不能仅凭文件后缀认定连接类型。

### 1.2 协议组成与标准化范围

SVNC 是基于 SSH 的远程桌面接入协议组合：SSH 提供安全传输、身份认证和通道复用；桌面使用 RFB；文件传输使用可选的 SFTP。标准化的对象是这些协议的接线方式、授权边界、生命周期和扩展约定。

```text
SVNC 客户端                         SVNC 服务端 / Agent
    │                                      │
    └──────── TCP / SSH 2 ──────────────────┤
             ├─ session → subsystem vnc ───┼─ 原始 RFB → 桌面后端
             ├─ session → subsystem sftp ──┼─ SFTP → 授权文件根目录
             └─ SSH global request ────────┴─ 可选元数据扩展
```

本草案定义单个服务端入口对应一个配置好的桌面后端。多个桌面通道仍访问同一桌面，不代表独立桌面或操作系统用户隔离。

连接配置使用 [`.svnc` 文件格式 v1](connection-file.md) 分享和导入。双击文件由客户端导入连接列表，文件格式版本与本接入协议版本独立。

桌面采集方式、DXGI/X11、后端进程、客户端 UI、本地 WebSocket 桥接、凭据存储、配置文件格式、审计落盘格式和部署方式属于实现。JumpServer 资产授权、审批、录像、会话分配和撤权接入属于上层产品集成。它们不构成本草案的线上报文。

“必须”表示互通或权限边界所需的要求；“应”表示推荐行为；“可”表示可选能力。标为“当前实现”的细节用于说明现状，不自动成为所有实现的要求。

## 2. 入口、身份与授权

1. SVNC 入口必须运行 SSH 2。项目默认 TCP 端口为 `5922`，端口可配置；该默认值不表示已注册的标准端口。
2. 客户端必须校验服务端 SSH 主机密钥。首次信任应通过可信预置或用户明确核对完成，主机密钥变更不得被静默接受。
3. 基线身份认证为 SSH 用户名与公钥认证。当前 Agent 将一个配置用户名绑定到一份公钥列表，不支持 SSH 密码认证和 SSH 用户证书。客户端连接普通 SSH 隧道时的其他认证能力，不代表 SVNC Agent 支持它们。
4. SSH 认证成功仅表示可以继续申请已授权的服务。桌面访问和文件访问必须分别授权；某项服务被拒绝不应使另一项已授权服务不可用。
5. 服务端可按部署设置连接数、通道数、认证频率、握手超时和空闲超时；具体数值不是协议常量。

基线桌面服务端必须实现 `vnc` 子系统。SFTP 是可选能力。当前 Agent 也支持仅开启 SFTP 的部署，该部署提供文件服务，但不应被描述为可用的 SVNC 桌面服务。

## 3. 桌面通道

### 3.1 建立

SSH 握手和认证完成后，客户端执行以下步骤：

1. 发送 `SSH_MSG_CHANNEL_OPEN`，通道类型为 `session`，无额外通道数据。
2. 通道打开成功后，发送以下通道请求，并等待成功响应：

```text
byte     SSH_MSG_CHANNEL_REQUEST
uint32   recipient_channel
string   "subsystem"
boolean  TRUE                  # want_reply
string   "vnc"
```

这里的 `string`、`uint32` 和 `boolean` 使用 SSH 的二进制表示。子系统名区分大小写。

服务端必须检查桌面权限，并在成功连接配置的桌面后端之后，回复 `SSH_MSG_CHANNEL_SUCCESS`；不能满足请求时回复 `SSH_MSG_CHANNEL_FAILURE`。成功打开后，每个通道只能运行这一个子系统。

### 3.2 数据

请求成功后，普通 SSH channel data 直接承载完整的双向 RFB 字节流，服务端首先发送后端的 RFB 版本标识，例如以下 12 字节：

```text
RFB 003.008\n
```

上述 `\n` 表示一个换行字节，不是反斜杠和字母 n。

必须满足以下约定：

- 不在 RFB 前增加 SVNC 标识、JSON、长度头或版本包，不在数据中混入日志。
- SSH 数据包边界没有 RFB 消息语义。客户端和服务端必须按连续字节流解析，支持拆包和合包。
- RFB 的版本、安全类型、像素格式、编码、输入与剪贴板能力按 RFB 及双方支持的扩展协商，Agent 透传这些数据。
- SSH 登录成功不跳过 RFB 安全握手。当前托管后端使用独立 VNC 密码认证，客户端仍需提供相应凭据；外部后端按自己的安全类型处理。
- RFB 编码与扩展不能仅凭“SVNC”名称推断。Tight、JPEG、光标、多屏、缩放和文本剪贴板的具体支持取决于桌面两端；文件传输使用 SFTP。

RFB 3.8 是推荐互通目标；旧版本按 RFB 规则处理。本草案不新增 RFB 版本号。只读桌面策略必须在服务端或后端执行，不能仅依赖客户端隐藏输入控件。

### 3.3 生命周期与失败

单向 EOF 按 SSH 通道语义处理，不应立即丢弃反方向尚未读取的数据；双向结束后关闭通道。当前 Agent 对 SSH 通道和后端 TCP 使用半关闭。异常、连接关闭或服务端退出可终止通道；客户端必须处理不完整的 RFB 会话。

正常桌面结束不依赖 SSH `exit-status`，当前 Agent 不发送该状态。客户端不能把缺少 `exit-status` 当作仍可读写桌面的证明。

子系统请求失败只提供通道级成功/失败，当前没有稳定的 SVNC 错误码。客户端不能可靠地区分服务不支持、桌面无权限和后端不可达。SSH 请求成功也只表示后端连接已建立，RFB 认证或初始化仍可能随后失败。

客户端不得因子系统失败而静默切换到裸 VNC 或不同身份认证方式。兼容隧道模式由连接配置明确选择。

## 4. 文件通道（可选）

文件服务在同一个 SSH 连接的新 `session` 通道中，通过 `subsystem` 请求名称 `sftp` 建立。客户端必须检查请求结果，再进行标准 SFTP 初始化。桌面与文件可同时使用不同通道，也可分别建立 SSH 连接。

文件协议基线为 SFTP version 3；服务端返回 `SSH_FXP_VERSION`。这里使用的是广泛部署的 SFTP v3 协议约定，对应历史 Internet-Draft，并非声称 SFTP v3 已发布为正式 RFC。客户端必须通过 SFTP 自身的版本和扩展信息处理兼容性。

授权模式如下；表中的允许仍受操作系统权限、路径边界与资源限制约束：

| 模式 | 读取文件 | 上传/写文件 | 列目录 | 查询指定路径元数据 | 创建目录、重命名、删除 |
| --- | --- | --- | --- | --- | --- |
| `disabled` | 拒绝 | 拒绝 | 拒绝 | 拒绝 | 拒绝 |
| `read_only` | 允许 | 拒绝 | 允许 | 允许 | 拒绝 |
| `write_only` | 拒绝 | 允许 | 拒绝 | 允许 | 允许 |
| `read_write` | 允许 | 允许 | 允许 | 允许 | 允许 |

`write_only` 表示禁止下载与目录枚举，仍允许修改和删除授权目录中的已有文件，并不表示只能投递新文件。当前协议未提供权限模式查询，客户端必须处理具体操作返回的拒绝。

文件路径使用以 `/` 为根的虚拟命名空间；`/` 映射到服务端授权根目录，而非宿主机文件系统根目录。客户端应发送规范化的绝对路径，使用 `/` 分隔；不得将宿主机的 Windows 盘符或绝对路径直接作为 SFTP 路径。

当前实现限制路径为最多 4096 字节，拒绝反斜杠、冒号、NUL，以及以空格或点结尾的路径分量，并限制普通文件访问。服务端必须阻止访问逃出授权根目录，并禁止创建符号链接、硬链接、变更属主和通过属性设置绕过策略。客户端应通过 SFTP 状态响应处理权限、大小、句柄或文件系统错误，不解析错误文本作为机器接口。

桌面只读不隐含文件只读；开启桌面也不隐含开启 SFTP。SFTP 成功不会授予桌面访问权限。客户端可在文件服务不可用时继续提供已授权的桌面功能。

## 5. 文件位置扩展（可选，现有私有名称）

当前名称为 `sftp-location@jumpvnc`。旧版的 `sftp-location@sshvnc` 保留为兼容别名，新客户端在旧服务端上自动回退。它是 SSH **全局请求**，不是 SFTP 扩展包，也不是桌面数据中的消息。此名称按现状记录，正式命名待第 10 节处理。

认证完成后，客户端可发送：

```text
byte     SSH_MSG_GLOBAL_REQUEST
string   "sftp-location@jumpvnc"
boolean  TRUE                         # want_reply
         <无请求特定数据>
```

文件服务已开启且请求数据为空时，当前 Agent 返回 `SSH_MSG_REQUEST_SUCCESS`，其响应特定数据是一个 UTF-8 JSON 对象，例如：

```json
{"root":"C:\\Users\\alice","home":true}
```

响应特定数据直接为 JSON 字节，不再加一层 SSH `string` 长度前缀，不需要行结束符。

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `root` | string | 授权文件根目录在宿主机上的绝对路径，供 UI 显示 |
| `home` | boolean | 该根目录是否为 Agent 运行账户的主目录 |

客户端不得用 `root` 拼出 SFTP 请求路径；无论显示路径为何，SFTP 根路径仍为 `/`。该扩展会向已认证且文件服务已开启的连接披露宿主机路径，实现方可不提供这一可选能力。

扩展不支持、文件服务关闭或请求带有额外数据时，当前 Agent 返回 `SSH_MSG_REQUEST_FAILURE`。客户端必须允许该扩展失败，并继续按标准 SFTP 尝试访问；失败不能被解释为文件服务一定关闭。不能要求旧 Agent 实现该扩展。

客户端应忽略未知 JSON 字段，并对响应大小、字段类型和显示内容进行校验。当前客户端接受的响应最多 16384 字节，`root` 必须非空、最多 4096 字节，且不包含 NUL、CR 或 LF；不可用时显示通用文件位置。这些校验发生在当前客户端收到响应之后，不代表 SSH 层的报文接收上限。

## 6. SSH 允许面与保活

当前 Agent 仅接受 `session` 和受限的 `direct-tcpip` 通道。`session` 只启动已授权的 `vnc` 或 `sftp` 子系统。Shell、命令执行、PTY、环境变量设置、X11、Agent 转发和远程端口转发不在允许范围内。未知请求必须按 SSH 规则拒绝；`want_reply` 为假时不发送请求响应。

子系统启动后，当前 Agent 拒绝后续所有通道请求。新的服务应使用新通道，不能在正在传输 RFB 或 SFTP 的通道上切换协议。

当前 Agent 支持空数据的全局请求 `keepalive@openssh.com`。客户端可用它维持空闲连接并检测对端存活；保活成功不表示桌面后端健康。未知全局请求不应使整个 SSH 连接失效。

## 7. 兼容接入

### 7.1 SSH 本地转发

兼容模式使用 SSH `direct-tcpip`，其目标必须精确匹配服务端配置的 IPv4 回环地址与桌面端口；当前实现要求 `127.0.0.1:<port>`，不将 `localhost` 或其他等价地址视为同一目标。

允许该转发仍需桌面权限。它不提供任意网络代理能力。SSH `-L` 和 `-D` 最终均使用此通道类型，受同一目标限制。客户端必须从兼容模式配置获取目标；标准 `vnc` 子系统无需客户端知道后端端口。

该模式适用于普通 VNC Viewer、guacd 和旧 Agent。客户端不得把 `vnc` 子系统失败直接当作启用此模式的授权。

### 7.2 裸 VNC 兼容入口

当前 Agent 可显式开启另一个 TCP 监听入口，将原始 RFB 转给同一后端。默认地址继承 SSH 监听地址，端口为 SSH 端口加一；默认配置下是 `5923`，也可另行配置。

该入口不经过 SSH 主机校验、用户认证或 SSH 加密，使用后端的 RFB 安全握手。它属于 VNC 兼容部署能力，不能被标注为 SVNC 安全连接。`5922` 不自动识别或接受裸 VNC。启用兼容入口必须保留后端认证，并按部署网络提供保护。

### 7.3 JumpServer 与 Guacamole 集成约定

本节约定上层系统如何区分接入方式，不增加线上报文，也不表示 JumpServer 或 guacd 已实现原生 SVNC 适配。

资产或连接系统应独立记录 `svnc` 与 `vnc`，不能因两者最终都使用 RFB 而合并接入类型，也不能仅凭端口号判断。默认端口只用于帮助录入，不是协议探测或服务身份凭据。

| 接入类型 / 模式 | 远端入口 | 建立桌面的方式 |
| --- | --- | --- |
| `svnc`（原生） | SSH，项目默认 TCP 5922 | 校验 SSH 主机密钥并认证，打开 `session` → `subsystem vnc`，再进行 RFB 握手 |
| `vnc`（直连） | 原始 RFB，通常 TCP 5900；本项目可选兼容入口默认为 5923 | 直接进行 RFB 握手，不申请 SSH 子系统 |
| `vnc` + SSH 隧道（兼容） | 显式配置的 SSH 入口及转发目标 | 使用 `direct-tcpip` 连接指定后端，再进行 RFB 握手 |

原生 `svnc` 连接所需的信息包括入口主机与端口、SSH 用户、认证凭据和可信主机密钥，以及 RFB 安全类型所需的独立凭据；不要求用户填写服务端内部桌面地址和端口。文件服务通过 `sftp` 子系统单独申请，不能因资产标为 `svnc` 就假定已获文件权限。

原生适配端应负责 SSH 生命周期与 `vnc` 子系统建立，再将 RFB 字节流交给桌面处理端。现有 Guacamole VNC 连接不能仅把目标端口改成 5922 就成为 SVNC 连接。尚未实现子系统适配时，可显式使用 §7.1 的本地转发方案，但需额外配置服务端允许的后端目标；这是兼容模式，不是原生 SVNC 的必选能力。两种方式均需将会话关闭、授权收回与 SSH 连接及通道的释放关联起来。

当前 JumpVNC Viewer 内部用 `transport: "subsystem"`、`"vnc"`、`"forward"` 分别记录上述三种方式。这是已有客户端配置，不是线上协议字段，也不是已定义的 JumpServer 资产 API；上层集成需显式转换，不能直接把保存值改成 `"svnc"`。客户端不得根据产品名称、默认端口或子系统失败自动降级到另一种方式。

## 8. 版本与扩展规则

1. 本文 `v0.1` 是规范文档版本，不是线上握手版本。当前没有 SVNC 版本协商、能力查询或结构化控制通道；SSH 软件标识和 RFB 版本号均不能代替 SVNC 规范版本。
2. 本草案中的 `vnc` 通道始终以原始 RFB 开始，不能为了加入版本协商而在该通道前插入报文。
3. 可选元数据扩展失败时，基线桌面或标准 SFTP 应仍可独立工作。扩展发现不能扩大访问权限。
4. 新增不兼容的请求语义，应使用新的、正确命名的请求或子系统，并提供明确的支持检测方式；不能静默改变现有名称对应的字节流。
5. RFB 能力继续使用 RFB 协商，SFTP 能力继续使用 SFTP 协商。未来若增加 SVNC 能力查询，应只补充入口、服务和策略信息，不重复创建编码协商体系。
6. 规范版本、Agent 软件版本和桌面后端版本分别维护。兼容性说明必须写清适用规范及可选能力，不能只写“支持 SVNC”。

## 9. 互通验收与当前证据

符合桌面基线的实现至少应验证：

| 场景 | 预期 |
| --- | --- |
| SSH 身份或主机密钥不匹配 | 客户端无法进入可信桌面会话 |
| 申请 `vnc` 成功 | 首个应用字节为 RFB 版本标识，无 SVNC 额外前缀 |
| 分片与二进制传输 | 保留字节顺序和内容，包括 RFB 认证数据 |
| 桌面关闭、文件开启 | 桌面与兼容转发被拒绝，SFTP 仍可工作 |
| 桌面开启、文件关闭 | 桌面可工作，SFTP 和文件位置查询被拒绝 |
| 后端不可连接 | `vnc` 请求失败，不静默切换其他接入模式 |
| 同一连接同时运行桌面和文件 | 不混淆数据与权限 |
| 非允许 SSH 服务或转发目标 | 按 SSH 失败语义拒绝 |
| 可选位置扩展不支持或响应非法 | 不影响基线桌面；仍可尝试标准 SFTP |
| 文件路径、模式与大小限制 | 由服务端执行，客户端正确显示失败 |
| EOF、异常与超时 | 正确结束通道并释放相关资源 |

仓库已有相关测试位于：

- [`tests/integration/gateway_test.go`](../tests/integration/gateway_test.go)：子系统透传、同连接复用、独立权限、后端不可达、文件模式、目录隔离和位置查询。

这些测试是现有证据入口，不表示上表所有场景都已覆盖，也不替代独立实现间的互通验收。单连接复用多个 SSH 通道不提供桌面延迟保证；文件与桌面仍共享底层 TCP，性能应单独测量。

## 10. 冻结 v1.0 前的工作

1. **确定扩展名称与维护机制。** 产品名 JumpVNC、协议名 SVNC 及接入类型标识 `svnc` 按 §1.1 区分；仍需明确协议规范的维护方、变更评审和发布机制。SSH 子系统及请求名遵循 DNS 扩展命名约定；`vnc` 是当前非限定子系统名，不能据此声称已获得公共名称分配；`sftp-location@jumpvnc` 的后缀不是完整域名。正式公开前应确认公共名称的适用分配流程，或选择维护方实际控制域名下的限定名称，制定旧名称兼容与停用规则。本草案不直接改变任何线上名称。
2. **确定声明基线。** 明确 v1.0 的 RFB 最低互通版本、安全类型与 SSH 算法要求，以及文件能力和兼容入口如何声明。算法策略应随安全维护演进，不把当前依赖库默认值永久固化。
3. **决定是否增加能力查询。** 当前只能申请服务并处理失败；如需事先展示桌面权限、文件模式、大小限制、只读状态或后端能力，需要先定义请求、字段、大小上限、版本与隐私边界，再实现和验证。本草案不预设某个能力查询已经存在。
4. **确定错误与生命周期约定。** 当前只有 SSH/RFB/SFTP 原生错误；如需可区分的 SVNC 错误码、撤权通知或会话标识，应设计可选控制机制，并保留原始 RFB 流兼容性。不能把服务端日志中的原因当作线上错误接口。
5. **补齐独立互通证据。** 至少由一个独立客户端或服务端按本文实现并验收，补齐真实 RFB 握手、文件并发、半关闭、未知扩展和旧版本兼容用例，再发布 v1.0 及兼容矩阵。

后续可按“项目规范草案 → 稳定项目标准 v1.0 → 其他实现采用的公开互通规范”推进。第三方可只实现已声明的能力，不应要求依赖本仓库 UI 或某一种桌面采集引擎。

## 11. 协议依据

- [RFC 4254：SSH Connection Protocol](https://www.rfc-editor.org/rfc/rfc4254.html)，全局请求、通道、子系统、EOF 和转发的基础语义。
- [RFC 4250 §4.6.1：SSH 命名约定](https://www.rfc-editor.org/rfc/rfc4250.html#section-4.6.1)，限定扩展名使用维护方控制的完整域名。
- [RFC 6143：RFB](https://www.rfc-editor.org/rfc/rfc6143.html)，桌面协议基础与版本协商。
- [SFTP v3 历史草案 draft-ietf-secsh-filexfer-02](https://datatracker.ietf.org/doc/html/draft-ietf-secsh-filexfer-02)，文件协议参考；该草案已过期，未成为正式 RFC。
